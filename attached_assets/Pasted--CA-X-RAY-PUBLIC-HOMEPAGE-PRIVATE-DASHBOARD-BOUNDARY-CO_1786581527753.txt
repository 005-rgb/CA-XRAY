# CA X-RAY — PUBLIC HOMEPAGE & PRIVATE DASHBOARD BOUNDARY CORRECTION

## EXECUTION MODE

Implement this correction on the existing CA X-RAY project.

This is a **controlled information-architecture and routing correction**, NOT a redesign.

The existing visual identity, report design, typography, spacing language, colors, components, business logic, scan engine, provider adapters, persistence, authentication architecture, and billing architecture are valuable and MUST be preserved.

Make the smallest safe change set necessary.

Do NOT rebuild the application from scratch.

Do NOT introduce a new design system.

Do NOT rewrite the report UI.

Do NOT modify Phase 2 core engine behavior.

Do NOT modify provider adapters.

Do NOT modify PostgreSQL persistence architecture.

Do NOT modify Clerk/authentication implementation except where routing/visibility requires integration.

Do NOT implement Phase 5+ features.

# 5. AUTHENTICATION GATE FOR START SCAN

The CA input MUST remain publicly accessible.

A visitor should be able to:

1. Select network.
2. Enter contract address.
3. Click Start Scan.

However:

## If the visitor is NOT authenticated:

Do NOT start a private scan job yet.

Instead:

1. Validate the input.
2. Preserve the entered network.
3. Preserve the entered contract address.
4. Redirect to the existing authentication flow.
5. After successful authentication, return the user to the pending scan intent.
6. Do NOT require the user to enter the CA again.
7. Start the scan after authentication according to the existing scan architecture.

This is critical.

The user's scan intent must survive authentication.

Example:

Visitor enters:

Network = BNB Chain

CA = 0xABC...

Clicks:

Start Scan

Then:

Login

After login:

Resume scan for:

BNB Chain / 0xABC...

The user should not have to repeat the form.

Keep this visually subtle and consistent with the existing design.

# 12. SERVER-SIDE AUTHORIZATION

Frontend hiding is NOT sufficient.

For every private scan/report resource:

1. Verify authentication server-side.
2. Resolve the current user.
3. Resolve the user's workspace according to the existing Phase 4 architecture.
4. Verify ownership/membership.
5. Verify the requested scan belongs to the authorized workspace.
6. Reject unauthorized cross-workspace access.

Never trust:

* workspace_id from the browser
* user_id from request payload
* scan ownership supplied by client
* hidden frontend fields

The server remains authoritative.

Do not change the existing tenant architecture unless a concrete bug is found.

---

# 13. NO CROSS-TENANT REPORT ACCESS

This is a hard security requirement.

User A MUST NOT be able to access User B's report by changing:

`scanId`

in the URL.

Test:

User A requests User B's scan ID.

Expected:

403/404 according to existing security convention.

Never return the report data.

Do not reveal whether another user's scan exists if the current security model avoids resource enumeration.

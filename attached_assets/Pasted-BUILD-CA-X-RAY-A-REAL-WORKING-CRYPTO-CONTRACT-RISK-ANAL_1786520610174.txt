BUILD CA X-RAY — A REAL, WORKING CRYPTO CONTRACT RISK ANALYZER

This is a competition project. Build one small, trustworthy product:

PASTE CONTRACT ADDRESS → ANALYZE → EXPLAIN RISK → SHOW EVIDENCE

The product is a contract risk assessment tool. It is not an absolute
scam detector, investment adviser, trading terminal, wallet, or audit
replacement.

The highest priorities, in order, are:

1. A real working core
2. Real public data when available
3. Deterministic risk calculation
4. Evidence-based findings
5. A numerical reliability score separate from risk
6. A professional forensic report
7. A clean, readable UX
8. Low credit and low resource usage

STOP after the core product and report work. Do not expand the product
outside this specification.


==================================================
0. NON-NEGOTIABLE TRUST RULES
==================================================

1. Never fabricate live data.
2. Never invent, approximate, or silently replace an API result.
3. Never display UNKNOWN, UNAVAILABLE, or missing values as 0.
4. Never state or imply that a token is definitely a scam.

   - EVIDENCE
   - SOURCE
   - CONFIDENCE

11. If an API fails, show the actual failure or partial-data state. Do not
    substitute demo data or hardcoded live-looking values.
12. The report must say that it is an assessment based on available data
    at scan time, not financial advice.

5. SCAN MODES AND STATE MODEL
==================================================

Every scan has exactly one mode:

- LIVE
- DEMO

Every provider result has exactly one data status:

- VERIFIED
- DETECTED
- NOT_DETECTED
- UNKNOWN
- UNAVAILABLE
- DEMO
- ERROR

Definitions:

VERIFIED:
The provider explicitly verified the value or property.

DETECTED:
The provider explicitly detected the property or signal.

NOT_DETECTED:
The provider explicitly checked the property and reported that it was not
detected. This is not the same as UNKNOWN.

UNKNOWN:
The provider or available data cannot establish whether the property exists.

UNAVAILABLE:
The required endpoint, field, or provider is not available.

DEMO:
Deterministic fixture data used only by DEMO mode.

ERROR:
The request failed or returned an invalid response. Preserve the error
state and do not convert it into a value.

Rules:

1. DEMO data must never be mixed with LIVE data.
2. ERROR, UNKNOWN, and UNAVAILABLE must never silently become zero.
3. NOT_DETECTED is allowed to contribute a positive/no-risk signal only
   when the provider explicitly checked that capability.
4. A missing field is UNKNOWN, not NOT_DETECTED.
5. A provider timeout is ERROR or UNAVAILABLE, not NOT_DETECTED.

The visible scan states are:

- VALIDATING
- FETCHING DATA
- NORMALIZING DATA
- ANALYZING CONTRACT
- CALCULATING RISK
- CALCULATING RELIABILITY
- BUILDING REPORT
- COMPLETE
- PARTIAL DATA
- ERROR

Show only states that actually occur. Do not fake progress with arbitrary
timers or artificial delays.

7. DATA SUFFICIENCY AND CATEGORY STATUS
==================================================

Each of the six risk categories has:

- category score: 0–100, only when sufficient evidence exists
- category status: AVAILABLE, PARTIAL, UNKNOWN, or UNAVAILABLE
- evidence coverage: 0–100
- list of supporting evidence IDs

Category availability rules:

CONTRACT:
AVAILABLE when at least one direct contract-security capability result
exists and contract identity is validated. Verification status may be
separately UNKNOWN.

TRADING:
AVAILABLE when at least one direct trading-security or trading-restriction
result exists. Missing taxes alone must not make the whole category UNKNOWN.

HOLDER:
AVAILABLE when holder distribution or top-holder data exists. If no holder
data exists, status is UNKNOWN.

LIQUIDITY:
AVAILABLE when an actual pair and liquidity result exists. If no pair or
liquidity data exists, status is UNKNOWN.

DEPLOYER:
AVAILABLE when deployer identity or relevant deployment activity exists.
Unknown deployer behavior does not mean malicious behavior.

MARKET/PROJECT:
AVAILABLE when actual market data or independently verifiable project
signals exist. Missing website information alone must not erase available
market data.

A category may be PARTIAL when some required fields exist but other fields
are unavailable. PARTIAL categories may be used in scoring only if their
category evidence coverage is at least 50.

Category coverage must be calculated from explicit required fields, not from
the number of API calls.


==================================================
8. RISK ENGINE — EXACT SPECIFICATION
==================================================

The risk engine must be a pure deterministic local function:

same normalized scan snapshot + same rubric = same result.

Final risk score:

0–100, where higher means higher observed risk.

Original category weights:

- Contract Risk: 30%
- Trading Risk: 20%
- Holder Risk: 15%
- Liquidity Risk: 15%
- Deployer Risk: 10%
- Market/Project Risk: 10%

For available categories:

rawWeightedScore =
  contract × 0.30
  + trading × 0.20
  + holder × 0.15
  + liquidity × 0.15
  + deployer × 0.10
  + marketProject × 0.10

If one or more categories are UNKNOWN or UNAVAILABLE:

1. Do not award risk points for the unavailable category.
2. Do not treat the missing score as 0.
3. Redistribute only the original weights of available categories.
4. Normalize by the sum of available original weights:

normalizedFinalScore =
  sum(availableCategoryScore × originalCategoryWeight)
  / sum(availableCategoryWeight)

5. Show all omitted categories and their statuses.
6. Mark the result PARTIAL DATA.

Score eligibility:

A numerical FINAL RISK SCORE is allowed only when:

- contract category is AVAILABLE or PARTIAL with coverage >= 50
- trading category is AVAILABLE or PARTIAL with coverage >= 50
- total original weight of score-eligible categories is at least 60%
- contract identity and network are validated

Otherwise show:

INSUFFICIENT DATA FOR RELIABLE SCORE

Do not show 0 as a substitute.

Rounding:

- calculate internally using full precision
- clamp each category to 0–100
- clamp the final score to 0–100
- round the displayed final score to the nearest integer
- display calculation lines with at most two decimal places
- never return NaN or Infinity

16. RELIABILITY ENGINE — EXACT SPECIFICATION
==================================================

Reliability measures the strength of the analysis and its supporting data.
It is separate from the Risk Score.

Calculate six components, each from 0 to 100:

E = Evidence Coverage
S = Source Quality and Independence
F = Data Freshness
C = Cross-Source Consistency
R = Reproducibility and Traceability
I = Identity Validation

Overall Reliability Score:

reliabilityRaw =
  E × 0.35
  + S × 0.20
  + F × 0.15
  + C × 0.15
  + R × 0.10
  + I × 0.05

Clamp to 0–100 and round only for display.

Evidence Coverage E:

- explicitly supported required field: 100
- partially supported field: 50
- UNKNOWN or UNAVAILABLE: 0
- DEMO: excluded from LIVE coverage

Calculate E from weighted required fields across all six categories. Do not
calculate it from the number of successful network requests.

Source Quality S:

- two independent primary sources agree: 100
- one primary provider gives a direct result: 85
- one public chain or explorer endpoint gives a direct result: 70
- deterministic derived value with a complete source chain: 65
- indirect or project-claimed information: 30
- no evidence: 0

Freshness F for volatile data:

- age <= 15 minutes: 100
- age > 15 minutes and <= 1 hour: 85
- age > 1 hour and <= 24 hours: 60
- age > 24 hours: 30
- timestamp unavailable: 10
- data unavailable: 0

For static contract properties, a result retrieved during the current scan
may receive 100 freshness if the provider gives no older snapshot warning.

Consistency C:

- identity and values agree across sources: 100
- minor explainable discrepancy: 70
- unresolved provider conflict: 40
- contract or network identity mismatch: 0

Reproducibility R:

- same normalized snapshot always produces the same score, findings,
  reliability, and calculation trace: 100
- deterministic engine but incomplete traceability: 70
- partially reproducible result: 40
- nondeterministic or manually altered result: 0

Identity Validation I:

- valid address, supported network, and provider identity match: 100
- valid address but network or provider identity is incomplete: 50
- invalid address, unsupported network, or identity mismatch: 0

Reliability labels:

- 85–100: HIGH
- 65–84: MEDIUM
- 40–64: LOW
- 0–39: UNKNOWN

Reliability guardrails:

1. If identity validation I = 0, do not produce a final risk score.
2. If E < 40, show INSUFFICIENT DATA FOR RELIABLE SCORE.
3. If two or more core categories are UNKNOWN or UNAVAILABLE, reliability
   cannot exceed 59.
4. If there is an unresolved source conflict, reliability cannot exceed 74.
5. If volatile data has no usable timestamp, reliability cannot exceed 69.
6. If the scan is PARTIAL DATA, explicitly show the missing categories.
7. A high Risk Score with low Reliability is valid and must remain visible.
8. A low Risk Score with low Reliability must not be described as reassuring.

These caps are applied after calculating reliabilityRaw:

reliabilityScore = minimum(reliabilityRaw, all applicable caps)

Finding confidence:

MEDIUM:

LOW:
Limited, indirect, stale, or partially conflicting evidence.

- “Honeypot” requires an explicit strong malicious-trading signal or an
  equivalent direct test result from a reliable provider.
- “Liquidity is unsafe” is not allowed as a generic statement. Use the
  observed liquidity value and explain the applicable rubric threshold.
